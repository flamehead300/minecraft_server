# Configuration templates and provenance

`policy.json` is a documented overlay template, **not a complete server config**.
The renderer requires files generated by the pinned software and refuses missing
keys. It does not create guessed Paper YAML keys. Paper global/world defaults,
Bukkit, Spigot and Floodgate settings remain as generated until measurements
justify a reviewed change. No runtime-generated configs are committed because
they may contain identity, secret references or operator information.

Initial defaults cannot yet be captured: Java 25 and an operator-authorized first
boot/EULA acceptance are prerequisites. Repository tests use explicit synthetic
fixtures; they are not asserted to be server-generated defaults.

1. On an empty, access-restricted staging server, the operator reviews/accepts
   the EULA, starts exactly the pinned JARs, waits for startup, then sends `stop`.
2. Download the stopped server to `private/first-boot/` using supported transfer.
3. Run `python scripts/manage.py capture-defaults private/first-boot defaults/26.3-231`.
   This checks all three binaries and captures only the three expected config
   files. Retain startup logs privately to corroborate that these were generated
   by this release; checksums alone do not prove when a config was generated.
4. Run the command below with **allocated numeric ports** replacing the labels:

```text
python scripts/manage.py render-initial defaults/26.3-231 generated/initial --java-port JAVA_PORT --bedrock-port BEDROCK_PORT
```

The proposal contains only `server.properties`, `plugins/Geyser-Spigot/config.yml`
and a local manifest. Review diffs before uploading the two configuration files.
Comments and unrelated values are preserved. Source defaults are unchanged.
Floodgate's generated config and private key stay in place. Re-running into the
same destination fails safely. **Never run this initial-policy renderer against
production as an upgrade mechanism.** Manually migrate only reviewed differences
in a staged copy for upgrades; do not reapply initial policy over operator edits.

| Setting | Initial value | Purpose / gameplay effect |
| --- | --- | --- |
| `online-mode` | true | Authenticates Java accounts; retain throughout updates. |
| `white-list`, `enforce-whitelist` | true | Limits testing to explicitly admitted players. |
| `enforce-secure-profile` | false | Allows Bedrock chat without Java signed-profile keys; chat signing protection is reduced, Java account login remains online. |
| `gamemode`, `difficulty`, `hardcore` | survival, normal, false | Ordinary survival; deaths do not permanently exclude players. |
| `max-players` | 20 | Combined slot limit, not proof of capacity. |
| `view-distance` | 8 | Fewer chunks sent; shorter visible horizon. |
| `simulation-distance` | 6 | Smaller ticking area; distant crops, entities and farms may pause. |
| `enable-rcon`, `enable-query` | false | Use the panel console; no extra query/RCON listener. |
| `server-port` | allocated Java TCP port | Supplied explicitly; no guessed port. |
| Geyser `java.auth-type` | floodgate | Use Floodgate for Bedrock authentication. |
| Geyser `bedrock.transport` | nethernet | Current transport; requires separate Bedrock TCP+UDP allocation. |
| Geyser `bedrock.clone-remote-port` | false | Prevents a TCP conflict with Java. |
| Geyser `bedrock.port` | allocated Bedrock port | Same Bedrock number for TCP signaling and UDP gameplay. |
| Geyser `bedrock.webrtc-port` | 0 | Use the selected Bedrock port for UDP rather than another allocation. |
| Geyser `bedrock.signaling.mode` | builtin | Host signaling on the Bedrock TCP port; avoid depending on an external signaling service. |

Retain Geyser's generated integrated Java connection settings. Do not copy
standalone proxy settings into the Spigot plugin. Preserve Floodgate's `.`
username prefix and generated key. For this same-server plugin arrangement,
follow Floodgate's local integration; do not distribute its key to players.

Start with at most `-Xms2G -Xmx6G` inside the host's 8 GB cap, using supported
panel startup fields. Confirm units and the effective command; two GiB of nominal
headroom is a starting estimate for native buffers, thread stacks and other
process memory, not a guarantee. Measure panel/container total memory and reduce
heap if necessary. Never run another instance inside that same 8 GB allowance.

Record every tuning change with date, old/new value, reason, workload and measured
effect in `docs/results/`. Keep ordinary spawn rates and mechanics initially.
If exploration is the bottleneck, agree on dimensions, center and radius before
adding a separately pinned official pre-generation plugin. Do not generate an
unbounded world. A border restricts exploration and needs explicit agreement.
